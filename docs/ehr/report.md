# Phase 23 — EHR integration: impression, ICD-10-CM, and FHIR

Generated by `scripts/ehr_examples.py` and `scripts/verify_terminology.py`. Worked
examples: [`examples.md`](examples.md). Bundles: [`fhir/`](fhir/).

APEX's own JSON schema is fine for APEX. No hospital system reads it. This phase adds the
layer that turns a report into three things a clinical environment can actually consume:

1. **a single sentence** a clinician can paste into a note,
2. **ICD-10-CM code suggestions** a billing system can read,
3. **an HL7 FHIR R4 `Bundle`** an interface engine can ingest.

Available as `to_ehr_export(report)` and over HTTP at `POST /analyze/ehr`.

Most of the work is not plumbing. It is deciding what APEX is *entitled to claim* once its
output is expressed in code systems that carry legal and financial weight, and the two
sections below are that argument.

---

## 1. An ECG finding is usually not a billable diagnosis

This is the phase's central distinction and everything in the mapping follows from it.

For some findings the ECG **is** the diagnostic test. Complete AV block, atrial
fibrillation, right bundle branch block — these are defined by what the tracing shows, and
a 12-lead recording is sufficient to assert them. For most others the ECG only raises a
suspicion that a different test has to settle:

- **Myocardial infarction** requires a troponin rise and fall under the Fourth Universal
  Definition. Q waves on an ECG are not an MI; they can be positional or normal-variant.
- **Left ventricular hypertrophy** by voltage criteria agrees poorly with echocardiography,
  and ICD-10-CM's nearest code (I51.7 *Cardiomegaly*) is an anatomical diagnosis that
  imaging establishes.
- **Long QT syndrome** (I45.81) is a clinical and often genetic entity. A single prolonged
  QTc is far more often drug- or electrolyte-related than congenital.

So findings are split in two:

| Tier | n | Code emitted | Meaning |
|---|---|---|---|
| `ecg-definitional` | 25 | its specific code | the ECG establishes this |
| `ecg-suggestive` | 43 | **R94.31** | the tracing is abnormal; something else must say why |
| `not-codable` | 3 | *(none)* | normal ECG / physiological variant — not a diagnosis |

**R94.31 — *Abnormal electrocardiogram [ECG] [EKG]*** is the honest code for the middle
tier, and 43 of 71 findings land there. The more specific code a clinician might reach for
is not discarded: it travels as `candidate`, together with `requires`, the evidence that
would justify it. So `ASMI` suggests **R94.31**, and carries "I25.2 *Old myocardial
infarction* — requires documented infarction history; an ECG pattern alone does not
establish infarction". Visible for review, never auto-suggested.

A system that emitted I21.9 off a Q wave would not be helpful. It would be generating a
fraudulent claim.

## 2. ICD-10 encodes things a ten-second recording cannot see

The phase brief gives "I48.0 for paroxysmal atrial fibrillation" as the worked example.
That mapping is wrong, and the reason is worth stating because it generalises.

ICD-10-CM distinguishes **paroxysmal** (I48.0), **persistent** (I48.11 / I48.19),
**chronic** (I48.20), **permanent** (I48.21) and **unspecified** (I48.91) atrial
fibrillation. Those distinctions are about *duration and treatment history* — paroxysmal
means terminating within seven days — and none of them are present in ten seconds of
signal. A recording showing AF supports exactly one code: **I48.91, unspecified**.
Choosing I48.0 instead is upcoding: a more specific code than the documentation supports.
The rule is encoded as an executable test, not just a comment
(`test_atrial_fibrillation_is_unspecified_not_paroxysmal`).

The same trap recurs: atrial flutter typical vs atypical (I48.3/I48.4) needs the reentrant
circuit; second-degree AV block Mobitz I vs II is not in PTB-XL's label; infarct age is not
determinable from one tracing.

Phase 22 is relevant and still not sufficient. Serial comparison can show AF present now
and absent on a prior study, which is genuine evidence of an intermittent pattern — but
"intermittent on two tracings" is not the seven-day criterion, so the tier does not change.
It is the kind of evidence that belongs in front of a clinician, not in a claim.

## 3. Terminology is verified, not asserted

Every code was checked against the U.S. National Library of Medicine's Clinical Table
Search Service — **27 ICD-10-CM codes and 7 LOINC codes**, all passing three checks:

1. the code exists in the current release;
2. our `display` string matches the official description **exactly**;
3. the code is **billable** — a leaf, not a parent with children.

That third check earns its place. ICD-10-CM is revised every October and the revisions are
not cosmetic: **FY2024 subdivided I47.1 into I47.10/I47.11/I47.19**, silently turning a
billable code into a non-billable category header. A table written before that date would
still look right and would produce rejected claims. `make verify-terminology` re-runs the
whole check against the live service; `--offline` runs the structural half (coverage,
format, tier consistency) for CI without egress.

**Licensing.** ICD-10-CM is published by CDC/NCHS and is public domain, so codes are
reproduced directly. LOINC is © Regenstrief Institute under the LOINC License — individual
codes as identifiers are permitted, and no part of the LOINC database is redistributed
here, only the six codes emitted. SNOMED CT would require an affiliate licence and is
deliberately not used. (Same reasoning as Phase 21's corpus licensing.)

## 4. FHIR, and checking that it is actually FHIR

Output is a `Bundle` of type `collection`: a `DiagnosticReport`, an `Observation` per
finding, an `Observation` per measured interval, a `Device`, and a de-identified `Patient`.
Bundles in the examples run 10–16 resources.

Decisions that are easy to get wrong:

- **The Device does not go on `DiagnosticReport.performer`.** In R4 that element is
  `Reference(Practitioner | PractitionerRole | Organization | CareTeam)` — software is not
  an allowed performer. The spec-correct home is `Observation.device`, which every finding
  and measurement carries; report-level attribution rides on an extension so a consuming
  system can detect machine generation mechanically instead of grepping the prose.
- **`DiagnosticReport.status` follows the review gate.** `final` asserts a result fit to
  act on. Whenever APEX flags anything for review the status is `preliminary` — 4 of the 7
  examples.
- **Findings are values, not codes.** Each finding Observation uses LOINC **8601-7**
  (*EKG impression*) as `code` and puts the finding in `valueCodeableConcept`, carrying the
  SCP label and its ICD-10-CM mapping as two codings of one concept — which is what a
  `CodeableConcept` with multiple `coding` entries means.
- **Model confidence is an extension.** No R4 element means "the classifier's probability",
  so it gets a named extension rather than being smuggled into a field that means something
  else.
- **No PHI, ever.** APEX never receives patient identity. Supply `patient_reference` and no
  Patient resource is generated at all; otherwise a Patient carrying only an opaque
  identifier — no name, birth date, or address — is emitted, and a test asserts those
  fields are absent.

### The validator needed help

Bundles are validated with `fhir.resources` against the published R4B
StructureDefinitions. Probing it with deliberately broken bundles showed it is **necessary
but not sufficient**:

| Injected fault | Schema check |
|---|---|
| `Observation` missing required `status` | caught |
| `DiagnosticReport` missing required `code` | caught |
| `valueQuantity.value` non-numeric | caught |
| malformed `dateTime` | caught |
| extension with two `value[x]` | caught |
| `"status": "definitely-final"` | **missed** |
| `"type": "not-a-bundle-type"` | **missed** |
| Device referenced from `DiagnosticReport.performer` | **missed** |

The misses are all the same shape: `code` primitives whose *required ValueSet binding*
lives outside the StructureDefinition's type system, plus reference-target rules the
schema cannot see. So `check_bindings()` adds the required bindings for every coded element
emitted here, resolves every internal reference, and checks it against the allowed target
types. All eight faults above are now caught, and the suite tests the validator on broken
input rather than only on good input — a validator only exercised against valid data is
indistinguishable from one that always returns "fine".

## 5. Examples

Seven categories: PTB-XL's five diagnostic superclasses plus two rhythm cases they do not
reach. Each is a real held-out test-fold record run through the actual detector and the
Phase-22 interval measurement — nothing hand-written.

| Category | Record | ICD-10-CM | Report status |
|---|---|---|---|
| Normal ECG | 9 | *(none)* | `preliminary` |
| Myocardial infarction | 63 | `R94.31` | `preliminary` |
| ST/T change | 963 | `I48.91`, `R94.31` | `preliminary` |
| Conduction disturbance | 598 | `I44.4`, `I44.7`, `I48.91`, `I49.8`, `Z95.0` | `preliminary` |
| Hypertrophy | 1522 | `R94.31` | `final` |
| Atrial fibrillation | 318 | `I48.91`, `R94.31` | `final` |
| Paced rhythm | 2587 | `Z95.0`, `R94.31` | `final` |

All seven bundles validate. Two are worth looking at:

**Normal ECG (record 9) emits no ICD-10 code at all**, which is correct and is the tier
system working: a normal ECG is not a diagnosis, and the encounter reason — which APEX does
not know — is what gets coded.

**Paced rhythm (record 2587) emits Z95.0**, *Presence of cardiac pacemaker*: a status code
describing the patient, not a disease.

**Selection is on detector output, and stated.** Choosing records purely on annotation
produced two examples that never exercised their own mapping — record 116 is annotated NDT
but the detector saw only sinus rhythm, and record 382 is a paced rhythm the detector read
as atrial fibrillation, so the Z95.0 path was never reached. Examples now pick the first
held-out record where the detector surfaces the category, and each prints its annotation
next to what was detected so disagreements stay visible. Detector accuracy is Phase 12's
subject and is not relitigated here.

## 6. Limitations

- **The mapping is authored, not official.** It is verified for existence, wording and
  billability, but no payer or coding authority has reviewed the *clinical* choice of code
  for each finding. Treat it as a defensible starting point for a coding team, not a
  substitute for one.
- **Codes are US ICD-10-CM.** WHO ICD-10 and national variants differ, and ICD-11 is not
  addressed.
- **R4B only.** R5 moves several elements this module uses (notably around
  `DiagnosticReport`); no R5 bundle is emitted and none is claimed.
- **No US Core profile conformance.** Bundles are valid base FHIR R4B. US Core adds
  must-support elements and slicing that a real deployment would have to satisfy, and
  validating against those profiles needs a terminology server this project does not run.
- **Terminology bindings are not value-set-validated.** Codes are checked against NLM for
  existence and wording; membership of coded elements in their bound ValueSets is checked
  only for the four required bindings enumerated in `fhir.py`.
- **The impression is deterministic template text.** It is consistency-clean by
  construction for the same reason as Phase 6's templater, and equally incapable of
  nuance a human reader would add.
